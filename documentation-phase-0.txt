# Phase 0 — PDF Extraction and Arabic Text Preparation

## Objective

The first phase of the Egyptian Labor Law RAG project was to convert the official 112-page Egyptian Labor Law PDF into a reliable Arabic text corpus suitable for later article parsing, chunking, embeddings, and retrieval.

The PDF presented several extraction challenges, including:

* Arabic Presentation Form characters
* Incorrect Arabic character ordering
* PDF-specific Private Use Area (PUA) characters
* Arabic diacritic glyphs encoded through a custom font
* Tatweel characters
* Spaces incorrectly inserted inside Arabic words
* Repeated Egyptian Gazette headers
* Other isolated PDF text-extraction artifacts

Because this is a legal document, the cleaning process was deliberately conservative. Only transformations that were investigated and validated were applied. Broad automatic Arabic-space joining or speculative Unicode replacements were avoided.

The final RAG corpus contains the substantive legal text from pages 1–111. Page 112 was excluded because it contains publisher/deposit and administrative material rather than additional labor-law articles.

---

# Step 1 — Initial Arabic Extraction Problem

## Problem

The first extraction of the PDF using `pdfplumber` produced Arabic text that was not immediately suitable for NLP processing.

Two major issues were identified:

1. Arabic Presentation Form characters were present.
2. Characters within Arabic words were stored in an incorrect order.

For example, text that visually represented a word such as:

```text
سنة
```

could be stored internally as:

```text
ةنس
```

This needed to be investigated at the Unicode level rather than assuming that the problem was only a terminal or display issue.

---

# Step 2 — Unicode Normalization and Arabic Bidirectional Ordering

## 2.1 Unicode inspection

We used Python's `unicodedata` module to inspect the actual Unicode code points produced by the PDF extraction.

Characters such as:

```text
ﺔ
ﻨ
ﺳ
```

were identified as Arabic Presentation Form characters.

These are compatibility characters rather than the standard Arabic Unicode characters normally preferred for NLP processing.

## 2.2 NFKC normalization

Unicode NFKC normalization was tested:

```python
unicodedata.normalize("NFKC", text)
```

This successfully converted compatibility characters into standard Unicode characters.

For example:

```text
ﺔﻨﺳ
```

became:

```text
ةنس
```

However, the character order was still incorrect.

The characters were confirmed at the Unicode level to actually be stored as:

```text
ة → ن → س
```

rather than:

```text
س → ن → ة
```

Therefore, the problem was not simply visual rendering.

## 2.3 Manual reversal test

A manual character-reversal approach was tested but rejected.

Although reversing Arabic characters could correct some words, it also reversed numbers and other left-to-right content.

For example:

```text
٢٠٢٥
```

could incorrectly become:

```text
٥٢٠٢
```

and:

```text
١٨
```

could become:

```text
٨١
```

Therefore, manually reversing the extracted text was considered unsafe.

## 2.4 Unicode Bidirectional algorithm

The `python-bidi` package was then tested:

```python
from bidi.algorithm import get_display

text = get_display(text)
```

After applying the Unicode Bidirectional algorithm, the Arabic character ordering was corrected while preserving mixed-direction content such as numbers and punctuation.

Examples included:

```text
ةنس → سنة
ددعلا → العدد
ىف → فى
```

The resulting character sequences were also inspected at the Unicode level to verify that the correction was not merely a visual terminal effect.

## Result

The first validated processing sequence became:

```text
PDF
 ↓
pdfplumber
 ↓
NFKC normalization
 ↓
Unicode BiDi processing
 ↓
Corrected Arabic character ordering
```

# Step 3 — Investigation of Arabic Character Variants

After correcting the main Unicode and ordering problems, additional unusual Arabic characters were investigated.

A character-frequency analysis using `collections.Counter` identified several Arabic-related characters, including:

```text
ی  U+06CC  Persian Yeh
ھ  U+06BE  Heh Doachashmee
ـ  U+0640  Arabic Tatweel
```

Extended Arabic-Indic digits were also present.

These characters were not automatically replaced because unusual Unicode does not necessarily mean incorrect Unicode. Some variants may legitimately occur in the source document.

This led to the decision that normalization should only be applied when the meaning of a character could be established with sufficient confidence.

# Step 4 — Investigation of Private Use Area Characters

## Problem

The extracted text contained characters from Unicode's Private Use Area (PUA), particularly:

```text
U+E821
U+E823
U+E825
```

Examples included:

```text
يعتبر
مقدما
قرارا
عاما
```

Private Use characters do not have a universal Unicode meaning, so they could not safely be replaced without investigating the PDF's font encoding.

## 4.1 Character-position investigation

The individual PDF character positions were inspected using `pdfplumber`.

The PUA characters shared positioning characteristics with neighboring Arabic characters, suggesting that they represented overlaid font glyphs rather than missing ordinary letters.

## 4.2 PDF font investigation

The PDF font resources were inspected.

The relevant font was identified as:

```text
FNTSBS+SimplifiedArabic
```

and was associated with the PDF's `F4` font resource.

## 4.3 ToUnicode mapping

The font's `ToUnicode` mapping was inspected.

The following mappings were identified:

```text
0105 → U+E821
0107 → U+E823
0109 → U+E825
```

This established that the PUA characters were intentionally produced by the PDF's font encoding.

## 4.4 Font structure investigation

The `SimplifiedArabic` font was identified as a Type0 font with a `CIDFontType2` descendant.

The PDF used:

```text
CIDToGIDMap = Identity
```

Therefore:

```text
CID 0105 → Glyph ID 0105
CID 0107 → Glyph ID 0107
CID 0109 → Glyph ID 0109
```

## 4.5 Embedded font extraction

The embedded TrueType font was extracted from the PDF:

```text
data/processed/SimplifiedArabic_embedded.ttf
```

The font was then inspected using `fontTools`.

The relevant glyphs were identified as:

```text
Glyph ID 261 (0x0105) → dammalow
Glyph ID 263 (0x0107) → fathatanlow
Glyph ID 265 (0x0109) → shaddalow
```

The font's Unicode mapping further confirmed:

```text
U+E821 → dammalow
U+E823 → fathatanlow
U+E825 → shaddalow
```

## Conclusion

The PUA characters were not corrupted Arabic letters.

They represented Arabic diacritic/mark glyphs that had been encoded using Private Use Unicode characters by the PDF's font.

Therefore, the following mappings were considered verified:

```text
U+E821 → Arabic Damma  ُ
U+E823 → Arabic Fathatan  ً
U+E825 → Arabic Shadda  ّ
```

For example:

```text
يعتبر
```

could safely become:

```text
يُعتبر
```

and:

```text
مقدما
```

could become:

```text
مقدمًا
```

# Step 7 — Investigation of Internal Arabic Spacing

## Problem

After solving the Unicode and font-related issues, another major extraction artifact was discovered.

The PDF contained spaces that appeared inside Arabic words.

Examples included:

```text
فـ ى
يكو ن
الت قيد
الط بية
```

while legitimate Arabic spaces also existed:

```text
قانون العمل
رئيس الجمهورية
مجلس النواب
```

Therefore, simply removing spaces between Arabic characters would have corrupted legitimate word boundaries.

## Initial investigation

A regular expression was used to identify patterns of:

```text
Arabic character + space + Arabic character
```

Approximately:

```text
23,212
```

potential matches were initially found.

This was too broad to repair automatically because the matches included both:

* genuine word boundaries
* incorrect PDF extraction spaces

## Testing extraction parameters

Different `pdfplumber` `x_tolerance` values were tested, including:

```text
3
5
7
10
```

The resulting text remained essentially unchanged.

This indicated that the problem was not caused by a simple extraction-tolerance parameter.

Character coordinates were then inspected and showed that some spaces were explicitly represented in the PDF's text layer.

Therefore, the spacing problem originated from the underlying PDF text representation.

---

# Step 8 — Comparing Extraction Methods

To determine whether the problem was specific to `pdfplumber`, the same pages were extracted using PyMuPDF.

The test used:

```python
page.get_text("text")
```

PyMuPDF produced similar artifacts.

This demonstrated that the problem was not specific to the extraction library.

Both libraries were interpreting the same problematic PDF text layer.

Therefore, the project continued using `pdfplumber`, while applying conservative post-processing to the extracted text.

---

# Step 9 — Conservative Arabic Text Repair

Because this is a legal document, the repair strategy was intentionally conservative.

The following principle was used:

> Do not automatically join every Arabic character separated by a space. Only repair patterns that have been confirmed to represent broken words.

## 9.1 Tatweel removal

Arabic Tatweel (`ـ`) was identified as a presentation-oriented stretching character.

Examples included:

```text
عقـود
العمـل
القـانون
```

These were safely normalized to:

```text
عقود
العمل
القانون
```

Tatweel removal was therefore included as a normalization step.

However, it was not treated as a solution to all spacing problems.

---

This conservative approach avoided applying broad Arabic-space removal rules that could damage legitimate legal wording.

# Step 13 — Search Boundary Investigation

During quality control, searches for short Arabic words such as:

```text
في
علي
```

appeared to produce unexpected matches.

For example:

```text
وفيما
فيها
فيه
```

contain the character sequence:

```text
في
```

but these are not necessarily standalone occurrences of the word `في`.

The Unicode code points were inspected and confirmed to be valid standard Arabic characters.

Therefore, this was determined to be a **search-boundary issue rather than text corruption**.

A raw substring search:

```python
"في" in text
```

cannot distinguish:

```text
في
```

from:

```text
فيها
```

For standalone Arabic searches, a Unicode-aware boundary expression can be used:

```python
re.findall(
    r"(?<![\u0600-\u06FF])في(?![\u0600-\u06FF])",
    text
)
```

The document itself was not modified to address this behavior.

This distinction is important because search logic and corpus cleaning are separate concerns.

# Step 14 — Investigation of Repeated Gazette Headers

## Problem

The extracted PDF contained a repeated Egyptian Gazette header on every page.

Examples included variations where the page number appeared at either the beginning or end of the line:

```text
الجریدة الرسمیة – العدد ١٨ (تابع) فى ٣ مایو سنة ٢٠٢٥ ٧٣
```

and:

```text
٧٤ الجریدة الرسمیة – العدد ١٨ (تابع) فى ٣ مایو سنة ٢٠٢٥
```

Because the page number changes from page to page, an exact repeated-line search initially did not identify the headers as identical.

## Validation

A page-aware regular expression was developed to identify the Gazette header while accepting the page number at either end.

The detection was validated against all 112 PDF pages.

The result was:

```text
Expected Gazette headers: 112
Detected Gazette headers: 112
Pages without detected header: 0
Page-number mismatches: 0
```

This established that the detected lines were the repeated Gazette headers rather than ordinary legal text.

## Production handling

The validated header removal was incorporated into:

```text
src/pipeline/build_knowledge_base.py
```

The header is removed during extraction rather than manually edited out of the final text.

This prevents repeated newspaper metadata from entering the RAG chunks and affecting retrieval.

# Step 19 — Parsing Articles into Structured Records

## Objective

The validated flat text corpus (`labor_law_clean_final_v2.txt`) confirmed that all 298 articles were present, correctly numbered, and free of known extraction defects. However, a flat text file is not yet suitable for retrieval: individual articles needed to be separated into structured records before chunking and embedding.

## Approach

Rather than re-deriving article boundaries independently, the parser reuses the exact heading-detection regex and page-tracking logic already validated in `check_article_headings.py`:

```python
r"^\s*مادة\s*\(\s*([٠-٩۰-۹0-9]+)\s*\)\s*:?\s*$"
```

This guarantees that article boundaries used for parsing are identical to the boundaries already confirmed to produce 298 headings with no gaps or duplicates, rather than introducing a second, potentially inconsistent detection pattern.

## Method

For each detected heading, the article's text is defined as everything between that heading and the start of the next heading (or end of file, for Article 298). Page-marker lines falling inside an article's range are stripped from the article body, since an article may legitimately span a page boundary and the marker itself is not part of the legal text.

Text appearing before Article 1 (the law's title and preamble, e.g. "قرر مجلس النواب...") is intentionally excluded from the output. This is a deliberate decision, not a defect: the preamble is not substantive article text a user would query, and including it risked it being retrieved for unrelated questions.

## Output

Each record contains:

```json
{
  "article_number": 27,
  "article_text": "...",
  "law_name": "Labor Law No. 14 of 2025",
  "source": "Official Gazette",
  "page": 21
}
```

Implemented in:

```text
src/pipeline/parse_articles.py
```

Output saved to:

```text
data/processed/labor_law_articles.json
```

## Validation

The parser includes built-in sanity checks, and the results were independently reproduced twice — once during development and once by re-running the script from a clean environment against the same validated input file, with identical output confirmed both times:

```text
Total records: 298
Expected: 298 | OK
Missing article numbers: None
Duplicate article numbers: None
Articles with suspiciously short/empty text (<5 chars): None
Shortest article text length: 59
Longest article text length: 6767
Average article text length: 468.0
```

The longest article (Article 1, 6,767 characters) is the law's definitions article, containing 38 defined terms — consistent with expectations and a useful sanity signal that article boundaries were captured correctly rather than merged or truncated. The shortest and last article (Article 298) was manually spot-checked and confirmed to be a complete, self-contained provision with no leftover or truncated content.
