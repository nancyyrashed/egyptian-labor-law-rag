# Phase 4 — FastAPI Backend, Streamlit Frontend & Latency Tuning

This covers turning the Phase 2 pipeline into a working application: the
FastAPI backend (`src/api/main.py`), the bilingual Streamlit frontend
(`src/frontend/streamlit_app.py`), and a latency pass driven by real timing
measurements rather than guesses — instrumentation, a diagnosis showing the
LLM call (not retrieval) was the wait, and three targeted fixes, re-verified
against the Phase 3 evaluation.

## 1. FastAPI backend (`main.py`)

The backend wraps the existing pipeline behind one HTTP endpoint. No RAG logic
is duplicated: `load_resources()` and `ask()` are imported directly from
`ask.py` (via a `sys.path` insert), the same pattern `evaluate_phase3.py`
already used.

**Resources load once, at startup.** The embedding model, Chroma collection,
and Groq client are created in a `startup` handler and stored in a module-level
`_resources` dict — not per request. Re-loading the embedding model on every
call would have made each question far slower than it needs to be.

**Endpoints:**

| Endpoint | Purpose |
|---|---|
| `GET /health` | Returns `{"status": "ok", "ready": <bool>}` — `ready` is true once startup has finished loading resources. |
| `POST /ask` | Takes `{"question": "..."}`, runs the Phase 2 pipeline, returns the response shape below. |

`/ask` returns an `AskResponse` (validated by a Pydantic `response_model`):
`question`, `answer`, `retrieved_articles`, `cited_articles`, `is_abstention`,
and `hallucinated_citations`. These are exactly the fields the frontend needs
to show the answer, render citations, show abstentions differently, and surface
the internal hallucination check — nothing from `ask()`'s internals (like raw
distances or chunk text) is exposed.

**Error handling.** A live endpoint has no equivalent of the evaluation loop's
"record the failure and keep going" pattern, so each failure mode gets a
distinct, recoverable response instead of a raw 500:

| Situation | Response |
|---|---|
| Empty / whitespace-only question | 400, Arabic message |
| Request arrives before startup finished | 503, Arabic "still loading" message |
| Groq rate limit (exception with `status_code == 429`) | 429, Arabic "too many requests" message |
| Any other failure (timeout, network, etc.) | 500 with a generic Arabic message; the real exception type and text are printed server-side only, not leaked to the client |

The 429 check uses `getattr(e, "status_code", None)` rather than importing a
specific Groq exception class, so it doesn't depend on the SDK's exception
hierarchy. See section 6 — it has not yet been exercised by a genuine rate
limit through the API.

**Sync endpoint, on purpose.** `ask_endpoint` is a plain `def`, not
`async def`. FastAPI runs sync endpoints in a worker threadpool, so the
blocking Groq call doesn't stall the event loop and other requests (including
`/health`) stay responsive while one question is being answered.

**CORS** is currently `allow_origins=["*"]` so a locally-run Streamlit app on a
different port can call the API. Flagged in the code to be tightened to a
specific origin before public deployment (Phase 5).

## 2. Streamlit frontend (`streamlit_app.py`)

The frontend is a separate process from the API and talks to it over HTTP
(`requests.post` to `http://localhost:8000/ask`, 30-second timeout), matching
the planned FastAPI + Streamlit architecture. Run it in its own terminal after
starting the API.

**Bilingual, Arabic-first.** Every user-visible string lives in one `TEXT`
dictionary keyed by language, so both languages stay in sync. Arabic is the
default; a single toggle button switches to English and back. The Arabic layout
is right-to-left (direction switched by CSS per language), with Amiri for
headings and Tajawal for body text; English uses Source Serif 4 and Inter. The
language toggle only changes the UI — the backend and its Arabic system prompt
are unchanged.

**Visible disclaimer.** A "legal information, not legal advice" notice is
rendered at the top of the page in the selected language on every load, not
only inside model answers. This is the Phase 4 plan's checkpoint requirement,
and it matches the disclaimer the system prompt already forces into every real
answer.

**Rendering an assistant response** (`render_assistant()`), by case:

| Case | Rendering |
|---|---|
| Abstention (`is_abstention`) | Shown as a warning box containing the model's fixed abstain phrase — visually distinct from a real answer. |
| Normal answer | Rendered as Markdown with `unsafe_allow_html=False`, so lists, bold text, and paragraphs the model produces display correctly without allowing raw HTML from the model. |
| Citations (`cited_articles`) | Rendered as "Source:" followed by one chip per article number (`مادة 90` / `Article 90`), HTML-escaped. |
| Non-empty `hallucinated_citations` | An error box naming the article numbers that were cited but never retrieved — the Phase 2 cross-check, made visible in the UI rather than only in logs. |
| API/network failure | Localized message chosen by failure type: connection refused (server not running), timeout, 429 (shown as a warning, not an error), or generic. If the backend supplied a `detail` message, that is shown instead. |

User-typed text is passed through `html.escape` before being displayed, since
it is inserted into an HTML wrapper.

**Interaction.** Session state holds the message history, the current language,
and a `pending` question. The four example questions (shown when the chat is
empty) and five sidebar topic questions use an `on_click` callback that stores
the question in `pending`, which is then submitted on the next rerun — the
standard Streamlit pattern for buttons that need to act like typed input. A
"new conversation" button appears in the sidebar once a conversation exists.

## 3. Latency: measuring before changing anything

**Problem:** answers felt slow. Before touching anything, the question was
where the time actually went — retrieval or generation. The knowledge base is
only 309 chunks (about 450 characters each), so retrieval was expected to be
cheap, and the API already loaded its model once at startup. That left the
Groq call as the prime suspect, but it was measured rather than assumed.

**Instrumentation.** `ask()` now wraps the two stages with
`time.perf_counter()`, prints `[timing] retrieve X.XXs | groq X.XXs` for every
question, and returns the numbers in the result dict (the API's response model
doesn't expose them; the evaluation script reads explicit keys, so the extra
field breaks nothing).

**Measurements (from real runs):**

| Run | Retrieval | Groq call |
|---|---|---|
| Phase 3 eval, question 1 (cold) | 5.12s | 1.02s |
| Phase 3 eval, questions 2–20 | 0.05–0.08s | 0.38–1.58s for Q2–Q6, then 5.76–14.81s for Q7–Q20 |
| Live API, first request after startup | 1.24s | 2.78s |
| Live API, later requests (6 samples) | 0.06–0.19s | 0.79–2.86s |

**Diagnosis.** Once warm, retrieval costs about 0.1s or less — negligible. The
wait is the Groq call. Two separate effects show up in the numbers:

- **Cold-start cost in retrieval.** The first retrieval after launch was far
  slower than every later one (5.12s in the eval script, 1.24s in the live
  API): one-time PyTorch initialization plus loading the Chroma index from
  disk on first use.
- **A sudden, sustained jump in the Groq call during the eval run.**
  Questions 2–6 took 0.4–1.6s each; from question 7 onward every call took
  6–15s. A step change that persists like this looks more like Groq's
  free-tier rate limiting (the SDK silently retries 429s with backoff) than
  the model itself getting slower. **This is a hypothesis, not a confirmed
  finding** — it was not tested (see section 6). Either way, the eval fires 20
  requests back-to-back, which real users don't, so the live-server numbers
  are the representative ones.

**Note on baseline:** timing instrumentation was added in the same change as
the fixes below, so no "before" measurement exists. Results are reported as
absolute numbers above, not as a before/after improvement percentage.

## 4. Three latency fixes

**Fix 1 — lower the model's reasoning effort.** `openai/gpt-oss-120b` is a
reasoning model: by default it generates hidden "thinking" tokens before
writing any of the answer, on every question. This task is extractive — find
the article, restate it, cite it — and doesn't need deep reasoning. `call_groq()`
now passes `reasoning_effort="low"` and `max_completion_tokens=1500`. Both are
read from environment variables (`GROQ_REASONING_EFFORT`,
`GROQ_MAX_COMPLETION_TOKENS`) so they can be tuned without editing code, and
setting `GROQ_REASONING_EFFORT` to an empty string omits the parameter entirely
(needed if the model is ever swapped for one that doesn't support it). The
token cap is deliberately generous because, for reasoning models, it counts
the hidden reasoning tokens too — a tight cap would truncate answers.

Because lowering reasoning effort can change answer behavior, the full Phase 3
evaluation was re-run afterward: **20/20, 100% retrieval hit rate, 100% citation
accuracy, 0% false abstention, 100% correct abstention, 0 hallucinated
citations** — identical to the pre-change result. No regression.

**Fix 2 — warm up at startup.** The cold-start cost from section 3 was being
paid by the first real user. `startup()` now ends with
`retrieve(embed_model, collection, "warmup")`, which exercises both the
embedding model and a Chroma query in one call, so the first user question
isn't the one that pays for PyTorch initialization and index loading.

The first version of this fix only ran `embed_model.encode(...)`. The live logs
then showed the first request's retrieval still taking 1.24s — the encode call
had warmed the model but not Chroma's first-query index load. That is why the
warm-up was changed to call `retrieve()` instead of `encode()` directly. (The
first-request retrieval time after this second change has not yet been
re-measured.)

**Fix 3 — cache repeated questions.** The example-question and sidebar buttons
send the same fixed text every time, and users repeat questions. `main.py` now
keeps an in-memory LRU cache (`OrderedDict`, max 500 entries) of successful
`AskResponse` objects, keyed on the question with whitespace collapsed. A hit
returns immediately with no retrieval and no Groq call — which also saves
free-tier rate-limit quota, not just time. Details that matter:

- Errors (429, 500) are never cached, only successful responses.
- Least-recently-used entries are evicted once the cache exceeds its limit.
- The cache is per-process and in memory, so it resets on every server restart.
- The key is the exact question text (whitespace-normalized), so two
  differently-phrased versions of the same question are separate entries.

**Deliberately not changed:**

- **`TOP_K` stays at 8.** Reducing it saves little (the prompt is only about
  3,500 characters) and 8 is the value that fixed the Article 156 miss in
  Phase 3.
- **The embedding model stays as-is.** It was chosen in Phase 1 on measured
  retrieval quality, and retrieval was never the slow part.
- **No streaming (yet).** Streaming the answer would make the first words
  appear sooner, but it is the largest change on the list: it means
  restructuring the frontend's custom message rendering and moving the
  citation/hallucination check to a final message sent after the text
  finishes. With warm answers arriving in roughly 1–3 seconds, the cost
  isn't justified yet. Revisit if real users on the deployed version find the
  wait too long.

## 5. Result

| Metric | Result |
|---|---|
| Retrieval time, warm | ~0.06–0.19s |
| Groq call, live API | 0.79–2.86s (6 sampled requests after the first) |
| Full question, live API | roughly 1–3s |
| Repeated question (cache hit) | effectively instant, no Groq call |
| Phase 3 evaluation after changes | 20/20, 0 hallucinated citations (unchanged) |

The local demo runs end to end: the Streamlit UI sends a question to the
FastAPI backend, which retrieves, generates, verifies citations, and returns a
response the UI renders with source chips and the disclaimer — the Phase 4
checkpoint.
